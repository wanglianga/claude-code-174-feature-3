# 县域农村自建房安全巡查整改补助平台

围绕**一栋房屋档案**打通「巡查 → 乡镇复核（整改方案）→ 风险告知 → 停用/人员转移 → 施工计划与补助资格校验 → 施工材料/照片/进度 → 逐项验收 → 县级销号 → 销号后复查」全链路，并把基层治理中的**协商成本**（户主、租户、经营者、老人家庭成员、村干部、施工队的态度与博弈）与 7 类异常事件沉淀在同一档案中。

**连续暴雨后险情处置（本次新增）**：暴雨后上报先经系统筛选（历史裂缝/上次复查结论/整改期限/家庭困难），只有真正需要重新上门的房屋才建立**风险事件**；同一房屋三天内反复上报自动并入同一条**持续升级事件**（等级只升不降），不再产生互不关联的通知；对整改期房屋给出**继续原计划 / 延长整改 / 先转移**三种分流，不重置原整改状态；升至转移级时**村干部、住建、民政收到同一处置任务**，困难家庭由民政并行落实临时安置与修缮补助，复查合格、三方任务办结销号后事件才闭环、风险等级恢复正常。

技术栈：Vue 3 + Vite + Element Plus + Pinia / NestJS 10 + TypeORM / PostgreSQL 15，Docker Compose 一键启动。

## 一、快速启动（Docker Compose 一键）

```bash
docker compose up -d --build
```

- 前端：http://localhost:8080
- 后端 API：经前端容器 nginx 反代在 http://localhost:8080/api （后端容器 3000 端口未直接发布到宿主机）
- PostgreSQL：容器内 `db:5432`，库名/账号/密码均为 `postgres`，数据库 `rural_house`

首次启动后端会**自动建表并写入演示数据**（9 栋覆盖各治理阶段的房屋、8 类角色账号、2 支施工队）。重置数据：

```bash
docker compose down -v && docker compose up -d --build
```

## 二、本地开发启动（不用 Docker）

需本机 Node.js ≥ 20、PostgreSQL ≥ 13。

```bash
# 1. 建库
createdb -U postgres rural_house   # 或用 psql: CREATE DATABASE rural_house;

# 2. 后端（默认连接 localhost:5432, postgres/postgres）
cd backend
npm install
# 如数据库账号不同，用环境变量覆盖：
# export DB_HOST=localhost DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_NAME=rural_house
npm run start:dev          # http://localhost:3000，首次启动自动建表+演示数据

# 3. 前端（新终端）
cd frontend
npm install
npm run dev                # http://localhost:5173 （已配置 /api 代理到 3000）
```

后端环境变量：`DB_HOST DB_PORT DB_USER DB_PASSWORD DB_NAME JWT_SECRET PORT`。

## 四、核心业务规则与"互相制约"设计

### 1. 风险规则引擎（巡查登记即自动定级）

输入房龄、层数、经营、出租、加层、墙体裂缝/屋面渗漏/地基沉降（无/明显/严重）、居住人数、雨季因素：

- **紧急转移**：地基沉降严重；或严重墙裂+加层；或雨季叠加严重结构隐患；或严重结构隐患+人员聚集；
- **暂停使用**：存在加层；结构隐患叠加经营/出租/多层/多人居住；墙裂+沉降双明显；雨季叠加结构隐患；
- **限期整改**：任一明显结构缺陷、严重渗漏、高房龄多层等；
- **一般关注**：仅老旧、轻微渗漏、经营出租登记等，纳入日常巡查。

### 2. 环节互相制约（后端强制，非前端提示）

| 环节 | 闸口规则 |
|---|---|
| 风险告知 | 方案要求停用/转移的，告知**必须签收**，否则不能封停、不能转移、不能开工 |
| 停用/转移 | 未告知签收不得封停；要求紧急转移的未落实安置不得开工；转移人员**验收销号前不允许返回** |
| 阻断异常 | 农户拒改、租户不搬、偷换材料、补助争议、验收不通过、问题反弹等未办结时，**冻结开工/验收/销号**；办结必须填写处置结果 |
| 施工开工 | 须同时满足：已告知（且按要求签收）→ 已停用/已转移 → 户主签署整改同意书 → 施工队资质有效 → 预算明细完整；任一不满足直接 400 |
| 材料核验 | 施工日志填写的进场材料名称+规格与预算明细自动比对，不一致即判定**偷换材料**，自动生成阻断异常 |
| 补助申请 | 8 项资格校验（困难类型、困难证明、权属证明、户主同意、方案告知、高风险停用/转移、预算、施工队资质）全过才进入乡镇复核；金额 ≤ min(预算70%, 5万) |
| 补助审批 | 存在未办结**补助资格争议**时禁止批准 |
| 补助发放 | 即使已批准，**未销号不得发放**（防"带病拨款"）；已发放不可重复发 |
| 验收 | 必改项逐条给出结论，且施工状态必须"已完成"；任一条不合格→整体不通过→退回整改并开阻断异常 |
| 销号 | 仅"验收通过待销号"可销号；县级须勾选"逐项完成"与"安全恢复/非数字销号"双确认；销号后准许转移人员返回 |
| 复查反弹 | 销号后复查 FAIL → 状态置为"问题反弹"、回写新隐患、开阻断异常；须重新复核→施工→验收→销号，支持多轮治理 |

### 3. 协商成本建模

- **利益相关方台账**：户主/租户/经营者/老人家庭成员/村干部，记录态度（支持/观望/抵触）与对进度的影响；
- **协商记录**：议题、参与方、协商结果，进入档案时间线；
- **7 类异常事件**：农户拒绝整改、偷换材料、补助资格争议、雨季风险加重、租户不愿搬离、验收不通过、复查反弹；区分是否阻断流程。

### 3.5 连续暴雨后风险事件（一条持续升级的事件，不是几条通知）

| 环节 | 规则（后端强制） |
|---|---|
| 是否重新上门筛选 | 输入历史裂缝/渗漏/沉降、上次复查/整改结论（方案、期限、是否已要求停用转移）、家庭困难类型、现场住人：隐患加重、研判达暂停使用及以上、整改期内出现结构隐患/严重渗漏、期限临近或超期、困难家庭现场仍住人 → 判定需上门并建立事件；否则只留痕、原计划不变 |
| 反复上报聚合 | 同屋存在未闭环事件时，新上报（含超过 3 天后的再报）一律并入；3 天窗口在升级记录中显式标注"三天内重复上报"；事件等级**只升不降**，上报次数累加 |
| 变化接回原档案 | 上报的裂缝/渗漏/沉降观测值回写房屋档案，但**不修改治理状态**：整改中的房屋继续整改、已停用保持停用，历史方案/期限/上次结论快照保存在事件上 |
| 住建三分流 | **继续原计划**（险情可控，村级加密监测）/ **延长整改**（新期限须晚于原期限，写延期记录、已完成工序保留）/ **先安排人员转移**；已达转移级禁止"继续原计划"；已分流事件不可重复分流 |
| 转移级三方同办 | 事件升至紧急转移（上报自动达到或分流确认）时一次性派发：村干部=组织转移+盯守，住建=紧急处置/方案调整+复查销号，民政=临时安置保障；困难家庭加派民政**修缮补助/救助**任务；重复上报与二次分流**不重复派单** |
| 临时安置并行 | 民政办结安置任务即生成人员转移安置记录与金额留痕；困难家庭临时安置与住建修缮补助**双通道并行**；安置人员在销号前**不允许返回**（沿用原闸口） |
| 闭环恢复 | 销号前校验该屋未闭环事件的处置任务全部办结（否则 400）；复查合格销号后事件自动关闭、房屋风险等级**恢复正常**、安置人员准许返回 |
| 复查反弹接回 | 销号后复查 FAIL 在开阻断异常的同时，建立/重开同构的风险事件（trigger=复查反弹），进入同样的分流与三方处置链路 |
| 部门权限 | 村干部仅可办结本乡镇村干部任务，住建任务仅住建/县/验收员，民政任务仅民政/县；跨角色或跨乡镇办结返回 403 |

### 4. 县级看到的不是"数量销号"

驾驶舱直接暴露治理真实性指标：高风险房屋总数与**真正停用/处置率**、高风险未停用督办清单（点进即可处置）、销号率与**反弹数**、整改项逐条完成率（含不合格数）、补助各环节数量与累计发放额、分乡镇对比。

### 已实际执行

1. **后端类型检查与生产构建**：`tsc -p tsconfig.build.json` 通过，`dist/main.js` 可由 `node` 直接启动。
2. **前端生产构建**：`vite build` 通过，`vite preview` 验证 `index.html` 与 JS 资源均 HTTP 200。
3. **全新 PostgreSQL 15 实例集成验证**：用编译产物对空库启动，自动建表+种子数据写入成功（18 个账号、9 栋房、3 条暴雨风险事件），登录签发 JWT 正常。
4. **端到端业务制约脚本（59 项断言全部 PASS，FAILED: NONE）**，除原有 21 项外，新增覆盖：
   - 暴雨上报筛选：无加重/期限宽裕 → 不建事件只留痕；整改期沉降渗漏加重 → 建事件；
   - 同屋三天内三次上报合并为一条事件（后两次 `merged=true`、reportCount=3），跨三天再报仍并入同一事件（=4），事件等级只升不降；
   - 三种分流：延长整改写延期记录且房屋状态保持"整改中"不重置；已分流不可重复分流；转移级禁止"继续原计划"；
   - 上报即达转移级 → 自动派发 4 项任务（村干部转移/住建处置/住建复查/民政安置，困难家庭再加民政修缮补助共 5 项），二次分流不重复派单；
   - 三方任务未办结、验收通过待销号时销号被拒（错误信息含未办结责任方）；住建/民政/村干部跨部门 403、外乡镇 403；
   - 民政安置办结自动生成转移记录且销号前不得返回；困难家庭修缮补助任务带金额办结；
   - 复查合格销号后事件 CLOSED、风险等级恢复 NORMAL、安置人员准许返回；
   - 销号后复查 FAIL 自动建立同构风险事件（F 房二次治理链路）；
   - 角色越权（农户上报暴雨险情 403）、乡镇数据隔离（外乡镇事件列表为空）、"我的任务"按角色只返回本部门任务；
   - 驾驶舱暴雨统计（事件数、未闭环、转移级、并入次数、筛除数、三方任务待办/办结、民政安置与修缮金额）。
